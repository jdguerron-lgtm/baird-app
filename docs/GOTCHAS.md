# Gotchas — Baird Service

Trampas conocidas. Léelo antes de tocar código sensible.

## Gotchas

- **Supabase client (actualizado 2026-10-07):** hay DOS y no se mezclan. **Server-side** (API routes, services, crons, auth de supervisor) → `import { supabaseAdmin as supabase } from '@/lib/supabase-admin'` (service_role, bypassa RLS; lanza si se importa en el browser o falta `SUPABASE_SERVICE_ROLE_KEY`). **Client-side** (páginas `'use client'`) → `import { supabase } from '@/lib/supabase'` (anon). Única excepción server con anon: `src/lib/auth/admin.ts` (`auth.getUser`). Nunca crees clientes nuevos con `createClient()` fuera de esos dos archivos. Historia y fases en `docs/PLAN-RLS.md`.
- **WhatsApp permanent token:** Using System User `baird-api` token. Never expires. If rotated, update `WHATSAPP_API_TOKEN` in Vercel + redeploy.
- **Serverless constraints:** In-memory state (Maps, setInterval) does NOT persist across Vercel invocations. El rate limit de `src/middleware.ts` es un `Map` en memoria → best-effort por isolate (10 paths cubiertos). Para un límite real hace falta un store externo (Upstash/KV) — pendiente.
- **Phone format (actualizado 2026-05-13):** el formato pipe (`57|3134951164`) es historia. Desde la migración `20260513_normalizar_telefonos.sql`, un trigger BD `normalizar_telefono_co()` normaliza `tecnicos.whatsapp` y `solicitudes_servicio.cliente_telefono` a dígitos puros con prefijo `57`. Para enviar a Meta usar siempre `phoneToDigits()` (alias `formatearTelefono`) de `src/lib/utils/phone.ts`. `parsePhone()` sigue tolerando pipe solo por datos históricos. Si cambias el algoritmo de normalización, sincroniza el TS con la función SQL.
- **Atomic acceptance:** `procesarAceptacion()` uses `UPDATE ... WHERE tecnico_asignado_id IS NULL` to prevent race conditions. Don't change this pattern.
- **Matching ciudad/especialidad/marca (2026-10-07):** TODO match de texto pasa por el pipeline `normalizeForMatch()` de `src/lib/utils/format.ts` (sin tildes, minúsculas, caracteres especiales → espacio, whitespace colapsado + trim). Para ciudades usar `cityTokenForMatch()` (primero corta por `/ , ; -` y luego normaliza) sobre `ciudades_cobertura` con fallback a `ciudad_pueblo`. Nunca filtrar ciudad con `.ilike()` en BD: es sensible a tildes ("BOGOTA" ≠ "Bogotá") e ignora la cobertura — así el panel de diagnóstico del admin mostraba como no habilitados a técnicos que SÍ fueron notificados.
- **Pedido de repuesto a supervisores sin repuesto (regla 2026-10-08):** `supervisor_repuesto_garantia_v1` SOLO sale si la solicitud tiene al menos un repuesto especificado (fila en `repuestos_pendientes` con SKU, no cancelada). `notificarRepuestoSupervisores` (botón admin + cron `repuesto-recordatorio`) devuelve `MSG_SIN_REPUESTO_ESPECIFICADO` sin enviar; `notificarCambioEstado` cae al aviso genérico `supervisor_cambio_estado_v1`; `/api/admin/cambiar-estado` rechaza con 400 el paso manual a `esperando_repuesto`. El único alta de repuestos es el diagnóstico del técnico (`/api/diagnostico`, que ya exige ≥1 producto con `esperar_repuesto`). Fuente única: `obtenerRepuestosEspecificados()` en `whatsapp.service.ts`.
- **ILIKE injection:** Always use `escapeLikePattern()` before interpolating user input into `.ilike()` queries.
- **Security headers:** Define in ONE place only (middleware.ts or next.config.ts), not both.
- **Portal token:** Each technician gets a `portal_token` UUID on first acceptance. Used for passwordless access to `/tecnico/{token}`. Never expose technician IDs in URLs.
- **Evidence storage:** Photos and signatures stored in Supabase Storage bucket `evidencias-servicio` (public). Path pattern: `{solicitud_id}/{timestamp}_{index}.{ext}`.
- **Límites de evidencia y videos (2026-10-20, topes ampliados 2026-10-24):** los topes viven en `src/lib/utils/media.ts` — fotos re-encodeadas a **4000 px / JPEG 0.92** (antes 2560 / 0.9) con tope 20 MB post-compresión; **video máx 50 MB por archivo por defecto y NO se puede subir solo desde código: es el techo por archivo del plan Free de Supabase** (sin `file_size_limit` propio en el bucket; el plan Pro de Vercel NO ayuda porque los archivos van del navegador directo a Supabase Storage). Un video más largo = varios clips (20 archivos en diagnóstico, 20 en completar, 30 por carga del admin). El tope de video se lee de `NEXT_PUBLIC_EVIDENCIA_VIDEO_MAX_MB` (10–5000, default 50): cuando el proyecto pase a **Supabase Pro** (US$25/mes, 100 GB de storage; el Free trae 1 GB y al 2026-10-24 ya iban ~480 MB), subir primero el "Upload file size limit" global en Supabase → Storage → Settings, luego la env en Vercel y redeploy — si la env supera el límite real de Supabase el upload falla con "Payload too large". La guía de duración (`videoSizeAdvice` → `segundosVideoAprox`, ≈1,25 MB/s) escala sola con ese tope.
- **Subida de evidencia "se queda pensando" (2026-10-24):** los formularios del técnico (diagnóstico y completar) ya NO suben con `supabase.storage.upload()` (fetch sin progreso ni timeout, todo en paralelo). Usan `src/lib/utils/subida-evidencia.ts`: `subirArchivoStorage` hace el mismo `POST /storage/v1/object/{bucket}/{path}` por **XMLHttpRequest** (cuerpo binario crudo + headers `apikey`, `Authorization`, `x-upsert`, `cache-control`, `content-type`; verificado contra el bucket real el 2026-10-24) con `upload.onprogress`, **corte por inactividad de 45 s**, **3 intentos** y fallback único a supabase-js si responde un 4xx distinto de duplicado. Ojo: Storage responde el duplicado como **HTTP 400 con `statusCode: "409"` / "The resource already exists"** — el helper lo trata como éxito (el intento anterior sí llegó). `ejecutarConLimite` sube **de a 3**; `comprimirConLimite` corta la compresión a 30 s y sigue con el original. Las vistas previas usan `crearMiniatura` (320 px) en vez del object URL del original — decodificar 10-20 fotos de 12-48 MP de la biblioteca para pintar cuadritos congelaba el celular. `tipoArchivoEvidencia` clasifica por MIME y, si viene vacío (galería de algunos Android), por extensión: antes esos archivos se descartaban en silencio. Si se cambia algo del endpoint o los headers, correr `src/__tests__/utils/subida-evidencia.test.ts` (XHR falso) y probar una subida real desde un celular. La evidencia del admin (`EvidenciaAdminSeccion`) y `PagoExternoForm` siguen con supabase-js. Toda galería debe renderizar con `MediaEvidencia` (`esUrlVideo`/`esUrlPdf`): `next/image` sobre un `.mp4` sale como imagen rota; `supervisorPdf` salta los videos. La evidencia que sube el admin es `nota_admin` con `payload.origen='evidencia_admin'` — al filtrar notas usa `esEventoEvidenciaAdmin()` para no mezclarlas.
- **Excel mapping:** `excel-mapping.ts` parses the specific Mabe/GE BITÁCORA format. Column indices are hardcoded to match that format — different Excel layouts will need a new mapper.
- **Cotizacion token:** For non-warranty, the quote approval token is stored inside the `cotizacion` JSONB column. The `/cotizacion/{token}` page scans all `cotizacion_enviada` records to find the match — there's no direct column index on this token. **Antipatrón conocido**: ver "Filtros JSONB" en sección Supabase Architecture; refactorizar a columna generada `cotizacion_token` con índice cuando crezca el volumen.
- **Estado pre-deploy:** antes de deployar verifica que las migraciones pendientes en `supabase/migrations/` ya estén aplicadas en producción. Si una migración falta, código nuevo que escribe a un estado inexistente o columna nueva fallará en runtime con un `CHECK violation` o `column does not exist`. **Cuidado especial con columnas JSONB**: si agregas un campo a un tipo TS (ej. `cotizacion`, `triaje_resultado`) que se persiste en una columna que aún no existe en la base, Supabase responde con `"Could not find the 'X' column of 'Y' in the schema cache"` y rompe el endpoint. Si creas una columna nueva, agrega `NOTIFY pgrst, 'reload schema';` al final de la migración para que PostgREST la reconozca sin esperar al refresh automático.
- **Parámetros de plantilla: Meta rechaza saltos de línea, tabs y 5+ espacios seguidos (error 132018) y tumba TODO el envío (2026-10-09):** `enviarPlantilla()` pasa ahora cada parámetro `{type:'text'}` por `sanitizarParametroPlantilla()` (colapsa whitespace, "-" si queda vacío), así ningún texto libre (dirección, novedades, nombre) vuelve a romper un mensaje. Caso real: la dirección "…recodo, 9.     502" hizo fallar `servicio_asignado_tecnico_v4` y el técnico nuevo quedó SIN enlace al portal → "no puede avanzar con el diagnóstico" (el portal del técnico no depende del pago del cliente; el mensaje al técnico sale ANTES del cobro del anticipo). Recuperación: botón "📲 Reenviar portal al técnico" en `/admin/solicitudes/[id]` (`reenviar-ultimo-mensaje` con `destinatario:'tecnico'`) y "Reenviar portal a técnicos con servicios activos" en `/admin/tecnicos` (`/api/admin/tecnicos/reenviar-portal`, un mensaje por técnico con su servicio activo más reciente). Los `[error]` de Vercel con `132018` son la señal; Hobby solo retiene 1 h de logs.
- **Nada de `void promesa` (fire-and-forget) en código server-side (2026-10-09):** en Vercel la función se congela apenas responde; una promesa sin `await` queda pendiente y se ejecuta minutos después (cuando la instancia se reusa) o nunca. Caso real: `registrarMensajeCliente()` (evento `mensaje_cliente` del historial) se llamaba con `void` en 19 sitios de `whatsapp.service.ts`; tras la carga masiva de 3 órdenes MABE el admin no vio en el historial que la plantilla de horario ya había salido y la reenvió → clientes con el WhatsApp duplicado. Hoy todo `registrarMensajeCliente` va con `await` (hay test: `src/__tests__/services/historial-mensaje-cliente.test.ts`). Si de verdad necesitas trabajo post-respuesta, usa `after()` de `next/server` como hace `/api/solicitar` con el geocoding. Complemento: el webhook registra los `status=failed` de Meta como evento `mensaje_cliente` (payload `entrega:'failed'`) en la solicitud activa del cliente, y "Reenviar último mensaje" refresca el historial al terminar.
- **Subida de fotos = SIEMPRE dos entradas, cámara en vivo + guardadas (2026-10-09):** `src/components/ui/SelectorFoto.tsx` renderiza dos `<input type="file">` ocultos: uno con `capture="user"|"environment"` (abre la cámara frontal/trasera) y otro sin `capture` (galería o explorador, aquí se puede sumar PDF vía `acceptGaleria`). No se puede hacer con un solo input: en iOS `capture` oculta la Fototeca y en varios Android salta el selector. Usado en /registro (perfil = cámara frontal, cédula = trasera), `ProductosNecesariosForm`, portal supervisor (guía + comprobante) y admin (contrato escaneado). Diagnóstico y completar ya tenían el mismo patrón con inputs propios. Si agregas un nuevo punto de subida de fotos, usa el componente en vez de un input suelto.
- **Fotos de /registro (perfil + cédula) se preparan en el navegador (2026-10-09):** `handleFileChange` llama a `prepararFoto()` (`src/lib/utils/foto-registro.ts`) ANTES de guardar el archivo en estado: detecta el tipo real por magic bytes (`sniffImageType`, manda sobre `file.type`, que Android a veces deja vacío y un PDF renombrado puede falsear), lo comprime/re-encodea a JPEG con `compressImageIfNeeded` (perfil 1600 px, cédula 2400 px; `forceReencode` para WebP/HEIC/GIF/BMP porque el JPEG puede pesar más que el original y aun así lo queremos) y recién ahí valida el tope de 5 MB. Antes se rechazaban fotos de celular >2 MB, WebP/HEIC y archivos sin extensión. HEIC solo se decodifica en Safari: en Chrome/Android el técnico recibe un mensaje para tomar la foto desde el formulario. `uploadImage()` (uploadHelpers) ya NO exige extensión en el nombre (la deriva de los magic bytes) y expone el mensaje real de Supabase en el error. Si un técnico reporta "no me deja subir la foto", pedirle el texto exacto del mensaje: distingue formato no decodificable / no es imagen / policy de Storage.
- **Storage público y PII:** los buckets `tecnicos-documentos`, `tecnicos-fotos`, `evidencias-servicio` están todos públicos via `getPublicUrl()`. La cédula del técnico es accesible a quien tenga la URL — pendiente migrar a `createSignedUrl()` (TTL 1h) en `src/lib/uploadHelpers.ts`. **No publicar URLs de documentos en lugares públicos**. **Desde 2026-10-10 `foto_documento_url` NO se le muestra ni se le envía al cliente**: el cliente ve el **carnet digital** (`src/lib/utils/carnet.ts`: foto perfil + nombre + número de documento, sin la imagen de la cédula). Si agregas una superficie nueva para el cliente, usa `CARNET_TECNICO_SELECT` + `construirCarnet()`; nunca selecciones `foto_documento_url` fuera de `/admin`.
- **RLS (estado tras Fase 4.1, 2026-07-11 — ver `docs/PLAN-RLS.md` § 3bis):** el server escribe con service_role (bypass RLS), así que las policies solo gobiernan al browser (anon). Cerradas al anon: `supervisores`, `llamadas`, `gps_pings`, `solicitud_eventos` (SELECT solo authenticated), `connection_errors` (idem), `pagos`, `cliente_historial`. Solo SELECT anon: `notificaciones_whatsapp` (`/aceptar`), `repuestos_pendientes` (`/verificar-paso`). Aún con writes anon `USING(true)`: `tecnicos` (`/registro` client-side) y `evidencias_servicio` (uploads client-side) — Fase 2/3. **Sigue deshabilitado en `solicitudes_servicio` (la tabla principal) y `especialidades_tecnico`** — ahí la seguridad depende 100% de tokens UUID en URLs y validación en API routes. Nunca expongas IDs sin token. Ojo: una `POLICY` no se aplica si la tabla tiene RLS off, así que las policies `anon_*`/`service_role_*` de `solicitudes_servicio` están definidas pero inertes.
- **Cliente Supabase singleton + sesión admin:** `src/lib/supabase.ts` es un único cliente con `persistSession` activo. Si el admin se loguea (`supabase.auth`) y luego abre un portal con token (`/tecnico`, `/servicio`...) en el MISMO navegador, los requests salen con rol `authenticated`, no `anon`. Por eso las policies de Storage deben scopearse a `public` (= anon + authenticated), no solo `{anon}` — si no, subir evidencia falla con `new row violates row-level security policy`. Ver `supabase/migrations/20260521_storage_policies_public_role.sql`.
- **WhatsApp 24h window:** Free-form text messages require the customer to have messaged the business within the last 24 hours. Template messages can be sent anytime. Always use templates for proactive outreach. Excepción deliberada (2026-10-20): el **resumen diario a supervisores** (`/api/cron/resumen-movimientos`) sale como texto libre porque no cabe en una plantilla; si Meta lo rechaza cae a `supervisor_resumen_diario_v1` (resumen en una línea). Para que el texto completo llegue, el supervisor tiene que haberle escrito a la línea ese día (basta un "ok").
- **Región de las funciones = la de Supabase (2026-10-22):** `vercel.json` fija `"regions": ["iad1"]` (Virginia) porque el proyecto Supabase `ceblicvdmephhktedsyv` vive en `us-east-1`. Antes era `gru1` (São Paulo): cada `await supabase` de una API route cruzaba Brasil↔Virginia (~120 ms) y rutas con 5-8 queries encadenadas + envíos a Meta sumaban segundos antes de responder ("el sistema es lento en dejar subir los textos"). Bogotá también está más cerca de Virginia que de São Paulo. Si algún día se migra la BD de región, mover `regions` con ella. Las páginas `'use client'` que consultan Supabase desde el navegador no pasan por aquí.
- **`.npmrc` con `legacy-peer-deps=true` (2026-10-22):** necesario para instalar `@vercel/analytics` / `@vercel/speed-insights`: sus peers OPCIONALES (`@sveltejs/kit` → vite 8) chocan con el vite 7 de vitest y npm 10+ aborta con ERESOLVE. El flag solo relaja esa verificación de peers; Vercel lee el mismo `.npmrc` al instalar. Ambos componentes van en `src/app/layout.tsx` y son no-op hasta activar Web Analytics y Speed Insights en el dashboard del proyecto.
- **Vercel Cron en plan Hobby:** solo crons diarios y pueden dispararse con hasta ~1 h de retraso. Un cron que dependa de "la hora exacta" debe calcular su ventana desde el corte más reciente ≤ ahora (patrón `ventanaResumen` en `resumen-movimientos.service.ts`), no desde `new Date()`.
- **Meta template names:** Must match exactly what's approved in Meta Business Manager. If deleted, there's a 4-week cooldown before reusing the same name — version the name instead (v1 → v2).
- **Cliente self-service token:** `solicitudes_servicio.cliente_token` es UUID durable, distinto de los demás tokens por acción (`horario_token`, `verificacion_paso_token`, `cotizacion.token`). Usado por `/servicio/{token}` y por las APIs `/api/solicitud/cancelar` + `/api/solicitud/reagendar`. Se genera al crear la solicitud (default DB + override server-side en `/api/solicitar`).
- **Link explícito al cliente para cancelar/reagendar** (2026-05-08): el componente `src/components/ui/GestionarServicioLink.tsx` se renderiza en TODOS los webviews del cliente (`/horario`, `/verificar-paso`, `/cotizacion`) con un copy que aplica a garantía y particular. Aplica a ambos flujos por igual. Se renderiza solo si la página tiene `cliente_token` en su data — ya cargado por todos los webviews relevantes. Desde 2026-07-06 el link también llega por WhatsApp: el botón de `horario_confirmado_cliente_v1` (enviada al confirmar horario) apunta a `/servicio/{cliente_token}`. `gestionar_servicio_v1` está APPROVED pero **sin disparo automático a propósito** (sería redundante con ese botón).
- **WhatsApp 24h y fotos del técnico:** las plantillas se pueden enviar en cualquier momento, pero los mensajes de tipo `image` (free-form) requieren que el cliente haya enviado un mensaje en las últimas 24h. Como el flujo customer-first no garantiza que el cliente escriba, las fotos del técnico se exponen también en `/servicio/{cliente_token}` para que la verificación de identidad no dependa del envío de imagen.
- **Cupo por franja es best-effort (2026-06-12):** `validarHorarioAgendable` (agenda.service) limita a `MAX_RESERVAS_POR_FRANJA` (=5 desde 2026-10-12; 3 el 2026-10-11, antes 2) las reservas activas por slot (día + franja, identidad = `fecha_visita_at` exacto) y bloquea agendar para el mismo día. Es read-then-write SIN lock: dos confirmaciones simultáneas del mismo slot pueden colarse ambas (quedarían 6). Aceptable al volumen actual; si crece, mover el conteo a una función SQL con `FOR UPDATE`. Ante error del conteo es **fail-open** (nunca bloquea agendar por una falla de BD). Cubre las 3 vías: confirmar-horario (incl. Dapta), reprogramar-repuesto y reagendar self-service.
- **El cupo por franja NO evita la sobre-agenda del técnico (2026-08-06, cupo 5 desde 2026-10-12):** `MAX_RESERVAS_POR_FRANJA` es un tope **global** del slot y no mira quién atiende — un mismo técnico podía llevarse todas las solicitudes de la franja y quedar en varias casas a la vez (pasó dos veces en prod). El guard por técnico es `tecnicoOcupadoEnSlot()` (agenda.service), aplicado en `procesarAceptacion` sobre el slot efectivo (el horario que el técnico eligió, o el ya confirmado si no cambió nada) **antes** del UPDATE atómico; si choca devuelve `reintentar: true` y la pantalla de aceptación muestra el aviso sin perder el servicio. Desde 2026-10-11 el tope es `MAX_SERVICIOS_TECNICO_POR_FRANJA` (=5 desde 2026-10-12; 3 el 2026-10-11) y cuenta **servicios Baird activos + bloqueos externos** de `agenda_tecnico_bloqueos` (los registra el técnico en `/tecnico/{token}/agenda`); un bloqueo con `bloquea_franja` cierra la franja sin importar el conteo. El (día CO, franja) de un `fecha_visita_at` sale de `slotDesdeFechaVisita` (`utils/agenda-slots.ts`) — si cambias franjas, sincronízalo con `FRANJAS_HORARIO`. **Si agregas otra vía por la que un técnico quede asignado a un `fecha_visita_at`, llámalo también.** Pendiente: reagendamientos de cliente/admin sobre solicitudes YA asignadas no lo chequean (pueden mover la visita a una franja donde ese técnico ya está al tope).
- **`triaje_resultado.codigo_falla` es NUMBER, no string (2026-08-06):** los códigos MABE son numéricos (`1844`, `13005`) y así quedan en el JSONB; `descripcion_falla` y `complejidad_falla` sí son string. Un `typeof v === 'string'` deja el código en null para TODAS las solicitudes — pasó en el listado del portal de supervisores y se detectó solo verificando en producción. Usar `campoFalla()` de `src/lib/utils/falla.ts`, que coerciona ambos tipos.
- **Recargo finde/festivo particular — no sumar a mano (2026-07-22):** `solicitudes_servicio.recargo_weekend_aplicado` es el libro mayor del recargo (0 o 6000 bruto) y `pago_tecnico` YA incluye los $5.400 del técnico. Todo punto que cambie la fecha de visita debe llamar `sincronizarRecargoFinDeSemana()` (recargo.service) — hoy: confirmar-horario, aceptación con cambio de horario, reagendamiento cliente/admin. El sync solo corre en estados pre-cotización; `/api/diagnostico` y `/api/cotizacion-precios` leen la columna y pasan `recargoBruto` a `calcularTarifaParticular`. Si agregas un writer nuevo de `fecha_visita_at`/`horario_confirmado`, agrégale el sync; si agregas un writer de `pago_tecnico` particular, súmale `recargoTecnicoDesdeBruto(recargo_weekend_aplicado)`. `esFinDeSemana()` (mabe.ts) ahora incluye festivos colombianos (`utils/festivos.ts`) y parsea también el texto español de `horario_confirmado` (antes `new Date(texto)` → Invalid Date → el recargo de garantía nunca se detectaba en UI).
- **`fecha_visita_at` es la identidad del slot — no cambiar su construcción:** `parsearFechaVisita` materializa día + hora de INICIO de franja (hora CO, +5 a UTC). El cupo por franja cuenta igualdad exacta de ese timestamp, y `franjasLlenasParaFecha` lo reconstruye con `FRANJAS_HORARIO[].horaInicio` — si cambias franjas u horas, sincroniza `constants/franjas.ts` con `extraerHoraInicio`. **Bug histórico (corregido + backfilled 2026-06-12):** el parser tomaba el primer número del texto ("14 de junio · 8am" → hora 14) porque extraía la hora del texto completo; ahora remueve el tramo "D de MES" antes de buscar la hora de la franja.
- **Fecha de visita: una sola función de validación, nunca reservar en el pasado (2026-10-22):** `validarFechaVisita(fecha, ahora?)` (`utils/fecha-visita.ts`) acepta `YYYY-MM-DD` o un ISO (`fecha_visita_at`), lo lleva a día CO y devuelve `{ ok, fechaYMD }` o `{ ok: false, motivo: 'formato' | 'pasada' | 'fuera_de_rango', error }`. Reglas: día real; **no anterior a hoy CO** (pedido de Juan: "no permitas que se reserve en fechas que ya pasaron"); no más de `MAX_DIAS_FECHA_VISITA_ADELANTE` (180) días adelante (un año mal tecleado). "Hoy" pasa y cada caller decide: las vías del cliente exigen además "mínimo mañana"; el admin lo admite con aviso. **La usan todos los puntos que reservan o cambian la fecha**: `validarHorarioAgendable` (agenda.service → confirmar-horario, aceptación del técnico eligiendo "el otro horario" del cliente, reagendar por link `/servicio`, reprogramar tras repuesto) y `POST /api/admin/reagendar-solicitud` (400 + `motivo`; la ficha usa `rangoFechaVisita()` como `min`/`max` del input y la misma función inline). **Si agregas otro writer de `fecha_visita_at`, llámala** — una fila con año absurdo desaparece del calendario, del cupo, de `/admin/incumplidos` y del resumen diario sin que nadie lo note. Por qué: la columna se materializa de dos fuentes y ninguna validaba el año. (1) `parsearFechaVisita` recibe "D de MES" sin año y lo infiere de la referencia: hasta el 2026-10-22 sumaba +1 año a cualquier fecha ya pasada, así que el técnico que aceptó con una opción vencida del cliente dejó la visita **un año adelante** (orden 9415568723: "29 de agosto" → `2027-08-29`). Ahora (`resolverAñoFechaVisita`) solo rota al año siguiente si la fecha pasó Y el año siguiente la deja a menos de `MAX_DIAS_ROLLOVER_AÑO` (180) días — el cruce diciembre → enero; si no, conserva el año de la referencia y `validarFechaVisita` la rechaza como pasada (`AceptarBoton` filtra esas opciones con la misma util de parseo). (2) El admin tecleó "2006"/"2008" en el `<input type="date">` y el route solo validaba el formato (órdenes 9415695001/9415696056). SQL de corrección de las 3 filas en `supabase/migrations/README.md` § "Correcciones manuales de datos".
